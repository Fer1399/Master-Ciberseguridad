# Incidentes de ciberseguridad: prácticas con PowerShell y Bash

Guía práctica para actuar como analista de un **SOC** (Security Operations Center): usar PowerShell (Windows) y Bash (Linux) para auditar, detectar, investigar, recoger evidencias y contener incidentes. Cada comando viene con lo que hace y el dato que importa.

> **Escenario:** un empleado avisa de que su equipo va raro. Se sospechan intentos de acceso fallidos, un proceso desconocido, conexiones de red extrañas y quizá un servicio no autorizado. Hay que detectar, recoger evidencias **antes de tocar nada**, analizar, valorar y proponer contención.

El recorrido sigue el ciclo de gestión de un incidente:

```text
Prevención → Detección → Monitorización → Evidencias
   → Investigación (OSINT) → Contención → Documentación → Seguimiento
```

---

## 1. Auditoría del sistema (prevención)

Antes de buscar un ataque hay que saber cómo está el equipo: usuarios, permisos, servicios, firewall y antivirus. Aquí se aplican el **mínimo privilegio** y el **hardening** (endurecer la configuración quitando lo innecesario).

### Windows (PowerShell)

```powershell
Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsBuildNumber
Get-LocalUser                                    # usuarios locales
Get-LocalGroupMember -Group "Administrators"     # quién es administrador
Get-Service | Where-Object Status -eq "Running"  # servicios en marcha
Get-NetFirewallProfile                           # estado del firewall
Get-MpComputerStatus | Select-Object AntivirusEnabled, RealTimeProtectionEnabled, AntivirusSignatureLastUpdated
```

- `Get-LocalGroupMember -Group "Administrators"` es clave: un administrador de más es una puerta abierta. Aquí se comprueba el **mínimo privilegio**.
- `Get-MpComputerStatus` dice si **Microsoft Defender** está activo y, sobre todo, cuándo actualizó las firmas por última vez (un antivirus sin firmas recientes no ve el malware nuevo).

### Linux (Bash)

```bash
uname -a                               # información del sistema y kernel
who                                    # usuarios conectados ahora
cat /etc/passwd                        # todos los usuarios del sistema
getent group sudo                      # quién puede usar sudo (admin)
systemctl --type=service --state=running   # servicios activos
sudo ufw status verbose                # estado del firewall UFW
apt list --upgradable                  # actualizaciones pendientes
```

- `getent group sudo` es el equivalente a mirar el grupo Administrators: quién tiene poder de root.
- `apt list --upgradable` enlaza con las **actualizaciones de seguridad**: software sin parchear es una vía de entrada típica.

## 2. Detección y monitorización (logs)

Los **logs** cuentan quién entró, cuándo y desde dónde. En Windows se consultan con `Get-WinEvent` y los **ID de evento**; en Linux con `journalctl` y los ficheros de `/var/log`.

### Windows: los ID de evento que hay que memorizar

```powershell
Get-WinEvent -LogName Security -MaxEvents 20     # últimos eventos de seguridad

# Intentos de inicio de sesión FALLIDOS (últimas 24 h)
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4625; StartTime=(Get-Date).AddDays(-1) }

# Inicios de sesión CORRECTOS
Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4624; StartTime=(Get-Date).AddDays(-1) }

# Instalación de un NUEVO SERVICIO
Get-WinEvent -FilterHashtable @{ LogName='System'; Id=7045 }
```

| ID | Significa | Por qué importa |
|---|---|---|
| **4625** | Inicio de sesión fallido | Muchos seguidos = posible **fuerza bruta** |
| **4624** | Inicio de sesión correcto | Un 4624 justo después de 200 fallos = el ataque funcionó |
| **7045** | Se instaló un servicio nuevo | Técnica de **persistencia** típica del malware |

> `-FilterHashtable` filtra en el propio motor de eventos (rápido), en lugar de traer todo y filtrar después. `StartTime=(Get-Date).AddDays(-1)` acota a las últimas 24 horas.

También conviene revisar lo que se ejecutó por consola:

```powershell
Get-WinEvent -LogName "Microsoft-Windows-PowerShell/Operational" -MaxEvents 30
```

### Linux

```bash
last                                             # historial de accesos
sudo journalctl -u ssh --since "24 hours ago"    # actividad del servicio SSH
sudo grep -i "failed password" /var/log/auth.log # contraseñas falladas
sudo grep -i "accepted" /var/log/auth.log        # accesos SSH correctos
sudo journalctl --since "24 hours ago"           # todo lo del último día
```

- `grep "failed password"` es el equivalente Linux al evento 4625: delata la fuerza bruta contra SSH.
- Según la distro, el log de autenticación está en `/var/log/auth.log` (Debian/Ubuntu) o `/var/log/secure` (RedHat/CentOS). `journalctl` funciona en ambas.

## 3. Procesos y conexiones de red

El objetivo: encontrar un **proceso sospechoso** y ver **con quién habla**. Lo potente es relacionar ambas cosas (qué proceso abrió qué conexión).

### Windows

```powershell
Get-Process                                      # procesos activos
Get-Process | Sort-Object CPU -Descending        # los que más CPU consumen

Get-NetTCPConnection -State Established           # conexiones abiertas
Get-NetTCPConnection -State Listen               # puertos a la escucha

# Relacionar conexión ↔ proceso (lo más útil)
Get-NetTCPConnection -State Established |
  Select-Object LocalAddress, LocalPort, RemoteAddress, RemotePort, OwningProcess

Get-Process -Id 1234                             # identificar el proceso por su PID
```

> El campo `OwningProcess` da el **PID**, y con `Get-Process -Id` sabes qué programa es. Así pasas de "hay una conexión a una IP rara" a "la abrió este ejecutable".

### Linux

```bash
ps aux                          # todos los procesos (con usuario y %CPU/%MEM)
ps aux --sort=-%cpu | head      # top procesos por CPU
ss -tunap                       # conexiones (TCP+UDP) con proceso asociado
ss -tulnp                       # puertos en escucha
ss -tn state established        # solo conexiones TCP establecidas
sudo lsof -i -P -n              # qué proceso usa cada conexión
```

Las letras de `ss` que hay que entender:

| Flag | Significa |
|---|---|
| `t` / `u` | TCP / UDP |
| `l` | solo los que están en escucha (*listening*) |
| `n` | no resolver nombres (más rápido, muestra IP y puerto) |
| `p` | mostrar el **proceso** dueño del socket |
| `a` | todos (escucha + establecidas) |

> Conceptos detrás de todo esto: **PID**, puertos en escucha vs conexiones establecidas, y la relación proceso ↔ conexión para detectar comunicaciones no autorizadas (por ejemplo, con un servidor de control del atacante).

## 4. Recopilación de evidencias (hashes)

Recoger pruebas **sin alterarlas** y poder demostrar que no se han tocado. Eso se consigue con una **función hash** (SHA-256): la huella digital del archivo.

### Windows

```powershell
Get-FileHash .\archivo.exe -Algorithm SHA256         # hash de un archivo

Get-ChildItem C:\Evidencias -File -Recurse |          # hash de toda una carpeta
  Get-FileHash -Algorithm SHA256 |
  Export-Csv C:\Evidencias\hashes.csv -NoTypeInformation
```

### Linux

```bash
sha256sum archivo.exe                                 # hash de un archivo
find ./evidencias -type f -exec sha256sum {} \; > hashes.txt   # hash de toda la carpeta
sha256sum -c hashes.txt                               # comprobar integridad después
```

> **Demostración clásica:** creas un `.txt`, calculas su SHA-256, cambias **una sola letra** y lo vuelves a calcular. El hash cambia por completo. Eso prueba que cualquier modificación se detecta → sirve para la **cadena de custodia**.

`sha256sum -c hashes.txt` vuelve a calcular los hashes guardados y avisa si alguno ya no coincide: así compruebas que las evidencias siguen intactas.

> **Sobre MD5:** se ve en apuntes, pero está roto para seguridad (se pueden fabricar colisiones). Para integridad de evidencias se usa SHA-256.
>
> **Importante:** estos comandos son una recogida *básica*. Una forense formal exige además preservar los originales y registrar fecha, zona horaria, responsable y método de adquisición.

## 5. Criptografía y comunicaciones seguras

Práctica con hashes, par de claves RSA, firma digital y certificados. Repasa los conceptos del repaso 2 (criptografía) de forma aplicada.

### Windows: certificados

```powershell
Get-ChildItem Cert:\CurrentUser\My       # certificados del usuario
Get-ChildItem Cert:\LocalMachine\My      # certificados del equipo
Test-NetConnection google.com -Port 443  # ¿llega al puerto HTTPS?
```

### Linux: OpenSSL

```bash
echo -n "Ciberseguridad" | sha256sum              # hash de un texto

openssl genrsa -out privada.pem 2048              # 1) generar clave PRIVADA (2048 bits)
openssl rsa -in privada.pem -pubout -out publica.pem   # 2) extraer la clave PÚBLICA

# Firmar un documento con la clave privada
openssl dgst -sha256 -sign privada.pem -out firma.bin documento.txt
# Verificar la firma con la clave pública
openssl dgst -sha256 -verify publica.pem -signature firma.bin documento.txt

# Ver el certificado TLS de una web
openssl s_client -connect google.com:443 -servername google.com </dev/null
```

> **La firma digital en dos pasos:** se firma con la clave **privada** (solo tú la tienes → autenticidad y no repudio) y cualquiera verifica con la **pública**. Si el documento cambia aunque sea un byte, la verificación falla (integridad).

Conceptos aplicados aquí: simétrica vs asimétrica, par de claves pública/privada, firma digital, certificados **X.509**, **PKI**, autoridades de certificación, **TLS** y el intercambio de claves **Diffie-Hellman**.

## 6. OSINT e investigación

Obtener información **pública** sobre dominios e IPs para investigar un indicador (IoC) sin tocar la infraestructura del atacante.

### Windows

```powershell
Resolve-DnsName google.com            # registros DNS
Resolve-DnsName google.com -Type MX   # servidores de correo
Resolve-DnsName google.com -Type TXT  # registros TXT (SPF, verificaciones...)
Test-NetConnection google.com -Port 443
tracert google.com                    # ruta de red hasta el destino
```

### Linux

```bash
dig google.com            # consulta DNS
dig google.com MX         # registros de correo
dig google.com TXT        # registros TXT
whois 8.8.8.8             # a quién pertenece una IP/dominio
ping -c 4 google.com
traceroute google.com     # ruta de red
```

| Registro DNS | Para qué |
|---|---|
| **A / AAAA** | Nombre → IP (IPv4 / IPv6) |
| **MX** | Servidores de correo del dominio |
| **TXT** | Texto libre: SPF, DKIM, verificaciones |

Herramientas web que completan la investigación:

- **VirusTotal** — analiza archivos, dominios e IPs contra decenas de motores.
- **AbuseIPDB** — reputación de una IP (¿ha sido denunciada por abuso?).
- **Shodan** — busca dispositivos y servicios expuestos en Internet.
- **URLScan.io** — analiza qué hace una URL/página.
- **Have I Been Pwned** — comprueba si un correo salió en filtraciones.

> **Precaución:** usa dominios, IPs y archivos de **laboratorio**. No subas evidencias reales con información confidencial a servicios públicos (al subir un archivo a VirusTotal, lo estás compartiendo).

## 7. Contención y respuesta

Limitar el daño: bloquear IPs, parar procesos, deshabilitar cuentas y detener servicios comprometidos.

### Windows

```powershell
Get-NetFirewallRule                               # reglas actuales

New-NetFirewallRule -DisplayName "Bloqueo IP sospechosa" `
  -Direction Outbound -RemoteAddress 203.0.113.50 -Action Block   # bloquear una IP

Disable-LocalUser -Name "usuario"                 # deshabilitar una cuenta
Stop-Process -Id 1234                             # matar un proceso
```

### Linux

```bash
sudo ufw deny from 203.0.113.50       # bloquear una IP con UFW
sudo ufw status numbered              # ver reglas numeradas
sudo systemctl stop nombre-servicio   # detener un servicio
sudo systemctl disable nombre-servicio# que no arranque al inicio
sudo kill -TERM 1234                  # terminar un proceso (señal TERM, ordenada)
```

> La IP `203.0.113.50` es de un rango **reservado para documentación**, no es real.
>
> **Advertencia operativa (muy importante):** no siempre hay que matar el proceso o apagar el equipo de inmediato. Primero se valora la **preservación de evidencias** (apagar borra la memoria volátil) y el impacto sobre los servicios. Contener bien es equilibrar cortar el ataque y conservar las pruebas.

## 8. Documentación y seguimiento

Automatizar la recogida en un script que crea una carpeta con fecha y vuelca todo dentro. Deja constancia ordenada para la investigación posterior.

### Windows (PowerShell)

```powershell
$Fecha = Get-Date -Format "yyyyMMdd_HHmmss"
$Ruta = ".\incidente_$Fecha"
New-Item -ItemType Directory -Path $Ruta

Get-ComputerInfo                       | Out-File "$Ruta\sistema.txt"
Get-Process                            | Out-File "$Ruta\procesos.txt"
Get-NetTCPConnection                   | Export-Csv "$Ruta\conexiones.csv" -NoTypeInformation
Get-Service                            | Export-Csv "$Ruta\servicios.csv" -NoTypeInformation
Get-WinEvent -LogName Security -MaxEvents 100 | Export-Csv "$Ruta\eventos_seguridad.csv" -NoTypeInformation

Write-Host "Recopilación finalizada: $Ruta"
```

### Linux (Bash)

```bash
#!/bin/bash
FECHA=$(date +%Y%m%d_%H%M%S)
RUTA="./incidente_$FECHA"
mkdir -p "$RUTA"

uname -a   > "$RUTA/sistema.txt"
who        > "$RUTA/usuarios.txt"
ps aux     > "$RUTA/procesos.txt"
ss -tunap  > "$RUTA/conexiones.txt" 2>&1
systemctl --type=service --state=running > "$RUTA/servicios.txt"
sudo journalctl -n 200 > "$RUTA/eventos.txt"

echo "Recopilación finalizada: $RUTA"
```

> Poner la fecha en el nombre de la carpeta (`$Fecha` / `$FECHA`) mantiene cada recogida separada y fechada. Para una forense real habría que ampliar los datos y sellar la integridad con hashes.

## 9. Práctica completa: investigación paso a paso

Caso: un servidor Linux recibe muchos intentos SSH y un Windows tiene conexiones que analizar. Las seis fases, con el comando de cabecera de cada una:

| Fase | Qué se hace | Comando clave |
|---|---|---|
| **1. Identificación** | Buscar accesos fallidos | `journalctl -u ssh` / evento `4625` |
| **2. Monitorización** | Procesos, servicios, puertos | `ps aux` + `ss -tunap` / `Get-Process` |
| **3. Evidencias** | Volcar logs y calcular hash | `sha256sum` / `Get-FileHash` |
| **4. Investigación** | Analizar IPs y dominios | `dig`, `whois`, VirusTotal, AbuseIPDB |
| **5. Contención** | Bloquear, deshabilitar, detener | `ufw deny` / `New-NetFirewallRule` |
| **6. Documentación** | Informe del incidente | script de recogida |

El **informe final** debe recoger: identificación, fecha/hora, sistemas afectados, descripción, evidencias, IoC, impacto estimado, medidas de contención, recomendaciones y seguimiento.

## 12. El ciclo completo (conclusión)

La idea de fondo: PowerShell y Bash cubren todas las fases de un incidente. El ciclo que reproduce la práctica:

```text
Prevención → Monitorización → Detección → Identificación
   → Investigación → Evidencias → Contención
   → Recuperación → Documentación → Seguimiento y mejora
```

Mapa rápido de qué comando sirve para cada parte del temario:

| Temario | En la práctica |
|---|---|
| Auditoría / prevención | usuarios, firewall y servicios |
| Criptografía | OpenSSL, SHA-256, certificados |
| Detección | Event Viewer (`Get-WinEvent`), `journalctl` |
| Monitorización | `Get-NetTCPConnection`, `ss` |
| OSINT | `dig`, `whois`, VirusTotal |
| Investigación | evidencias y hashes |
| Contención | firewall, procesos, servicios |
| Documentación | informes en CSV/TXT |

---

## Resumen en una frase

Con PowerShell y Bash se recorre el incidente entero: **auditar** el sistema, **detectar** en los logs (eventos 4625/4624/7045 en Windows, `auth.log`/`journalctl` en Linux), **relacionar procesos y conexiones**, **recoger evidencias con hash SHA-256**, **investigar** indicadores con DNS/WHOIS/OSINT, **contener** (bloquear IP, parar procesos y servicios) sin destruir pruebas, y **documentarlo** todo de forma trazable.
