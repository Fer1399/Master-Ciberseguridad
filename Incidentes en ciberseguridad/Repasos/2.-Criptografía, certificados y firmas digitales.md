# Resumen: Criptografía, certificados, firmas digitales y prevención

## 1. ¿Para qué sirve la criptografía?

Protege la información mediante técnicas matemáticas. Sus objetivos:

| Objetivo | Qué garantiza | Mecanismo típico |
|---|---|---|
| **Confidencialidad** | Solo quien debe puede leerlo | Cifrado (simétrico o asimétrico) |
| **Integridad** | No ha sido modificado | Funciones hash |
| **Autenticidad** | Viene de quien dice venir | Firmas digitales, certificados |
| **No repudio** | El firmante no puede negar haberlo firmado | Firma digital + marco jurídico |

> **Ejemplo:** cuando entras en la web de tu banco (`https://`), la conexión usa criptografía para que nadie lea tu contraseña (confidencialidad), nadie altere la transferencia (integridad) y sepas que la web es realmente la del banco (autenticidad).

---

## 2. Criptografía simétrica

**Una sola clave secreta** sirve para cifrar y descifrar.

```text
CIFRAR(Mensaje, Clave)    = Cifrado
DESCIFRAR(Cifrado, Clave) = Mensaje
```

- **Algoritmos:** AES, ChaCha20.
- **Ventaja:** muy rápida, ideal para grandes volúmenes de datos.
- **Problema principal:** ¿cómo comparto la clave de forma segura?

> **Ejemplo:** cifras un ZIP con la contraseña `Verano2026!`. Tu compañero necesita esa misma contraseña para abrirlo. Si se la envías por el mismo correo que el ZIP, cualquiera que intercepte el correo tiene las dos cosas.

> **Ejemplo real:** el cifrado de disco (BitLocker, FileVault) usa AES: gran cantidad de datos, una clave, rendimiento alto.

---

## 3. Criptografía asimétrica

Cada usuario tiene **un par de claves**:

- **Clave pública** → se comparte con todo el mundo.
- **Clave privada** → se guarda en secreto, nunca se comparte.

Lo que hace una clave solo lo "deshace" la otra. Algoritmos típicos: RSA, criptografía de curva elíptica (ECC).

### 3.1. Uso para confidencialidad

```text
Emisor cifra con la CLAVE PÚBLICA del destinatario
        ↓
Solo el destinatario descifra con su CLAVE PRIVADA
```

> **Ejemplo:** Ana quiere enviar un secreto a Bruno. Coge la clave pública de Bruno (está publicada) y cifra el mensaje. Aunque Carlos intercepte el mensaje y tenga también la clave pública de Bruno, no puede descifrarlo: solo la clave privada de Bruno sirve.

> **Analogía:** la clave pública es un buzón abierto donde cualquiera puede echar cartas; la clave privada es la única llave que abre el buzón.

### 3.2. Uso para firma digital

```text
Firmante opera con su CLAVE PRIVADA
        ↓
Cualquiera verifica con la CLAVE PÚBLICA del firmante
```

### Truco para no confundirse

| Quiero... | Uso la clave... | De quién |
|---|---|---|
| Cifrar para alguien | Pública | Del destinatario |
| Descifrar lo que me envían | Privada | Mía |
| Firmar | Privada | Mía |
| Verificar una firma | Pública | Del firmante |

### Simétrica vs. asimétrica

| | Simétrica | Asimétrica |
|---|---|---|
| Claves | 1 secreta compartida | Par pública/privada |
| Velocidad | Rápida | Lenta |
| Problema | Repartir la clave | Rendimiento; saber de quién es la clave pública |
| Uso típico | Cifrar muchos datos | Intercambio de claves, firmas |

## 4. Funciones hash (resumen)

Transforman una entrada de **cualquier tamaño** en un valor de **tamaño fijo** (digest).

Propiedades clave:

- **Unidireccional:** a partir del hash no se puede obtener el original.
- **Efecto avalancha:** un cambio mínimo en la entrada cambia el hash por completo.
- **Resistente a colisiones:** debe ser muy difícil encontrar dos entradas con el mismo hash.

> **Ejemplo (SHA-256):**
> ```text
> "hola"  → b221d9dbb083a7f33428d7c2a3c3198ae925614d70210e28716ccaa7cd4ddb79
> "Hola"  → e633f4fc79badea1dc5db970cf397c8248bac47cc3acf9915ba60b5d76b0e88f
> ```
> Solo ha cambiado una mayúscula y el resultado es totalmente distinto.

### Uso en integridad

> **Ejemplo:** descargas una ISO de Ubuntu. La web publica su SHA-256. Calculas el hash del archivo descargado:
> ```bash
> sha256sum ubuntu.iso          # Linux
> Get-FileHash ubuntu.iso       # Windows PowerShell
> ```
> Si coincide con el publicado, el archivo no se ha corrompido ni modificado.

⚠️ **Ojo:** el hash solo garantiza integridad, **no el origen**. Si un atacante modifica el archivo *y* el hash publicado en la web, no lo detectarías. Para garantizar el origen hace falta una **firma digital**.

> **Otro uso:** las contraseñas se almacenan como hash (con sal y algoritmos específicos como bcrypt o Argon2), no en texto plano.

### Algoritmos

- ✅ **Seguros:** SHA-256, SHA-384, SHA-512, SHA-3.
- ❌ **Obsoletos para seguridad:** MD5, SHA-1 (se han encontrado colisiones).

## 5. Firma digital

Asocia un documento con la clave privada del firmante.

### Proceso de firma

```text
DOCUMENTO → HASH → operación con CLAVE PRIVADA → FIRMA
Se envía: DOCUMENTO + FIRMA
```

### Proceso de verificación

```text
1. El receptor calcula el HASH del documento recibido.
2. Usa la CLAVE PÚBLICA del firmante para comprobar la firma.
3. Si todo cuadra → FIRMA VÁLIDA. Si no → NO VÁLIDA.
```

Garantiza:

- **Integridad:** si se cambia una coma del documento, la firma deja de ser válida.
- **Autenticidad:** solo quien tiene la clave privada pudo firmar.
- **No repudio:** el firmante no puede negar la firma (con el respaldo jurídico adecuado).

> **Ejemplo:** firmas un contrato PDF con tu certificado digital (DNIe o certificado de la FNMT). La empresa lo abre, el lector de PDF verifica la firma y muestra "Firmado por Luis Fernando Arrosquipa — documento no modificado". Si alguien cambia el importe del contrato después, aparecerá "La firma no es válida".

> **¿Por qué se firma el hash y no el documento entero?** Porque la criptografía asimétrica es lenta; firmar un resumen de 256 bits es mucho más eficiente que firmar un archivo de 50 MB.

⚠️ **Firma ≠ cifrado:** una firma no oculta el contenido; cualquiera puede leer el documento. Solo demuestra quién lo firmó y que no ha cambiado.

## 6. Certificados digitales

**Problema:** recibo una clave pública… ¿cómo sé que es realmente de quien dice ser?

**Solución:** un **certificado digital** vincula una identidad con una clave pública, y lo firma una **Autoridad de Certificación (CA)** de confianza.

Contenido típico (estándar X.509):

- Identidad del titular.
- Clave pública.
- Emisor (la CA).
- Periodo de validez.
- Número de serie.
- Algoritmos utilizados.
- Firma de la CA.

> **Analogía:** el certificado es como un DNI. El DNI vincula tu cara y nombre (identidad) y lo emite la Policía (CA), en quien todos confían. Cualquiera puede comprobar que es auténtico sin conocerte.

> **Ejemplo:** al pulsar el candado en `https://www.agenciatributaria.gob.es` ves su certificado: a quién pertenece, quién lo emitió y hasta cuándo es válido. Tu navegador confía en él porque confía en la CA que lo firmó.

> **Ejemplos en España:** certificado de persona física de la FNMT, DNI electrónico, certificados de representante de empresa.

## 7. PKI (Infraestructura de Clave Pública)

Conjunto de **tecnologías, políticas, procedimientos y componentes** para gestionar claves y certificados.

| Componente | Función |
|---|---|
| **CA** (Certification Authority) | Emite y firma certificados |
| **RA** (Registration Authority) | Verifica la identidad del solicitante antes de la emisión |
| **Certificados** | Vinculan identidad y clave pública |
| **CRL** (Certificate Revocation List) | Lista de certificados revocados |
| **OCSP** (Online Certificate Status Protocol) | Consulta en tiempo real si un certificado sigue siendo válido |
| **Políticas y procedimientos** | Emisión, renovación, revocación |

> **Ejemplo del ciclo:** para obtener el certificado de la FNMT, lo solicitas online, vas a una oficina a **acreditar tu identidad** (eso hace la **RA**) y después la FNMT (**CA**) emite y firma tu certificado.

### Revocación

Un certificado puede invalidarse **antes de caducar**.

> **Ejemplo:** te roban el portátil donde tienes instalado tu certificado. Debes **revocarlo** de inmediato. A partir de ese momento, cuando alguien compruebe una firma vía CRL u OCSP, verá que el certificado ya no es válido y la rechazará.

### Cadena de confianza

```text
CA RAÍZ (preinstalada en el navegador/sistema)
   └── CA INTERMEDIA
          └── Certificado del servidor / usuario
```

## 8. Diffie-Hellman (DH)

Permite que **dos partes acuerden un secreto compartido** a través de un canal público, **sin enviar nunca ese secreto**.

> **Analogía de la pintura:**
> 1. Ana y Bruno acuerdan públicamente un color base: **amarillo**.
> 2. Ana elige en secreto **rojo**; Bruno elige en secreto **azul**.
> 3. Ana mezcla amarillo+rojo → **naranja** y lo envía. Bruno mezcla amarillo+azul → **verde** y lo envía.
> 4. Ana añade su rojo al verde de Bruno; Bruno añade su azul al naranja de Ana.
> 5. Ambos obtienen **amarillo+rojo+azul = marrón**, el mismo color.
>
> Un espía ha visto amarillo, naranja y verde, pero "separar" la mezcla es muy difícil, así que no obtiene el marrón.

> **Ejemplo numérico (números pequeños, solo didáctico):**
> - Parámetros públicos: `p = 23`, `g = 5`
> - Ana elige privada `a = 6` → envía `A = 5⁶ mod 23 = 8`
> - Bruno elige privada `b = 15` → envía `B = 5¹⁵ mod 23 = 19`
> - Ana calcula `19⁶ mod 23 = 2`
> - Bruno calcula `8¹⁵ mod 23 = 2`
> - **Secreto compartido = 2** (nunca viajó por la red)
>
> En la realidad se usan números de miles de bits o curvas elípticas (ECDH).

### ⚠️ DH no autentica

DH por sí solo no sabe **con quién** está hablando → vulnerable a **Man-in-the-Middle (MitM)**:

```text
ANA ⇄ ATACANTE ⇄ BRUNO
```

> **Ejemplo:** en una Wi-Fi pública falsa, el atacante hace un DH con Ana (haciéndose pasar por Bruno) y otro DH con Bruno (haciéndose pasar por Ana). Lee y reenvía todo.

**Solución:** combinar DH con **autenticación** (certificados y firmas). En TLS/HTTPS, el servidor firma sus parámetros DH con la clave de su certificado.

---

## 9. Perfect Forward Secrecy (PFS)

Se usa **DH efímero** (DHE / ECDHE): una clave **nueva para cada sesión**, que se descarta al terminar.

```text
Sesión 1 → clave efímera 1
Sesión 2 → clave efímera 2
Sesión 3 → clave efímera 3
```

**Ventaja:** si en el futuro se roba la clave privada de largo plazo del servidor, **las sesiones pasadas siguen protegidas**.

> **Ejemplo:** un atacante graba durante un año todo el tráfico cifrado de una web. Después roba la clave privada del servidor.
> - **Sin PFS:** podría descifrar todo lo grabado.
> - **Con PFS:** no puede, porque cada sesión usó una clave temporal ya destruida.

TLS 1.3 exige intercambios de claves con PFS.

## 10. Todo junto: así funciona HTTPS (TLS)

| Paso | Mecanismo | Objetivo |
|---|---|---|
| 1. El servidor envía su certificado | Certificado + PKI | Autenticar al servidor |
| 2. El navegador valida la cadena y la revocación | CA, CRL/OCSP | Confiar en la identidad |
| 3. Intercambio de claves | ECDHE (firmado por el servidor) | Secreto compartido + PFS |
| 4. Transmisión de datos | AES o ChaCha20 | Confidencialidad rápida |
| 5. Control de cada mensaje | Hash/MAC (AEAD) | Integridad |

👉 **Idea clave:** la asimétrica se usa para **autenticar y acordar claves**; la simétrica, para **cifrar el grueso de los datos**.

### Tabla resumen de necesidades

| Necesidad | Mecanismo |
|---|---|
| Confidencialidad | Cifrado |
| Integridad | Hash |
| Autenticidad | Certificados / firmas |
| Intercambio de claves | Diffie-Hellman |
| Identidad criptográfica | Certificados |
| Gestión de confianza | PKI |

## 11. Plan de prevención y concienciación

Programa anual que combina **formación + concienciación + auditoría → evaluación → mejora continua**.

> **Ejemplo: reducir el phishing**
>
> | Fase | Acción | Resultado |
> |---|---|---|
> | 1. Diagnóstico | Simulación autorizada de phishing a 100 empleados | 20 hacen clic → **20 %** |
> | 2. Formación | URLs sospechosas, adjuntos, urgencia artificial, suplantación, cómo reportar | — |
> | 3. Concienciación | Carteles, emails, vídeos, alertas, mini-cuestionarios | — |
> | 4. Nueva evaluación | Segunda simulación | Ej.: 6 hacen clic → **6 %** (mejora del 70 %) |
>
> Además de bajar la tasa de clics, conviene medir cuántos **reportan** el correo sospechoso.

**Señales típicas de phishing:**
- Remitente parecido pero falso (`soporte@micr0soft-security.com`).
- Urgencia: "Su cuenta será bloqueada en 24 h".
- Enlaces cuyo destino real no coincide con el texto.
- Adjuntos inesperados (`.zip`, `.html`, macros de Office).

## 12. Auditoría interna

Verifica que las políticas **se aplican realmente**, no solo que existen.

**Checklist básico:**

- [ ] Política de seguridad y de contraseñas
- [ ] MFA donde corresponde
- [ ] Equipos actualizados
- [ ] Antimalware / EDR
- [ ] Copias de seguridad **y pruebas de restauración**
- [ ] Procedimiento de gestión de incidentes y registro
- [ ] Formación y campañas de concienciación
- [ ] Revisión de permisos y eliminación de cuentas innecesarias
- [ ] Revisión de dispositivos

**Ciclo:** Resultados → Hallazgos → Riesgos → Acciones correctivas → Seguimiento.

> **Ejemplo de hallazgo:**
> - **Hallazgo:** se hacen backups diarios, pero nunca se ha probado una restauración.
> - **Riesgo:** ante un ransomware, las copias podrían no servir.
> - **Acción correctiva:** prueba de restauración trimestral documentada.
> - **Seguimiento:** revisar en la próxima auditoría que se han hecho y registrado.

> **Otro ejemplo:** un empleado que dejó la empresa hace 3 meses sigue con la cuenta activa → eliminar la cuenta y crear un procedimiento de baja que avise a IT.

## 🧠 Ideas clave para recordar

1. **Simétrica = rápida pero con el problema de repartir la clave.**
2. **Asimétrica = resuelve el reparto, pero es lenta.** En la práctica se combinan.
3. **Cifrar** para alguien → su clave **pública**. **Firmar** → mi clave **privada**.
4. **Hash = integridad, no confidencialidad ni origen.** MD5 y SHA-1 están obsoletos.
5. **Firma digital = hash + clave privada** → integridad, autenticidad y no repudio.
6. **Certificado = identidad + clave pública firmadas por una CA.**
7. **PKI = todo el sistema** (CA, RA, CRL, OCSP, políticas).
8. **Diffie-Hellman acuerda un secreto sin enviarlo**, pero necesita autenticación para evitar MitM.
9. **PFS = claves efímeras por sesión**: robar la clave del servidor no descifra el pasado.
10. **La tecnología no basta:** formación, concienciación y auditoría cierran el ciclo.
