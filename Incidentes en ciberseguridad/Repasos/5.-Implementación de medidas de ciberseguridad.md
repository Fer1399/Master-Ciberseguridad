# Implementación de medidas de ciberseguridad

Los repasos anteriores iban de detectar e investigar incidentes. Este va de **prepararse y responder de forma organizada**: tener procedimientos escritos, capacidad para aguantar el golpe y recuperarse, saber quién decide, restaurar los servicios y aprender para la próxima.

---

## 1. Procedimientos de actuación (playbooks)

Un **procedimiento de actuación** define, para cada tipo de incidente, **qué hacer, quién lo hace, cuándo y cómo se documenta**. La idea es que, en plena crisis y con prisa, no haya que improvisar: se sigue la guía.

> Un **playbook** es justo eso: una guía paso a paso para un tipo concreto de incidente (playbook de ransomware, de phishing, de cuenta comprometida...). Cada uno baja al detalle de ese caso.

Las actuaciones persiguen cuatro objetivos, que conviene no mezclar:

| Objetivo | Qué busca |
|---|---|
| **Responder** | Actuar frente al incidente |
| **Mitigar** | Reducir sus consecuencias |
| **Eliminar** | Quitar la causa o lo malicioso |
| **Contener** | Que no se extienda |

El esqueleto que siguen casi todos los procedimientos:

```text
Incidente detectado → Identificación → Clasificación → Valoración
   → Contención → Erradicación → Recuperación → Seguimiento
```

Y adaptado a un caso concreto:

> **Playbook de malware:**
> ```text
> Detección → identificar equipo afectado → aislarlo
>   → preservar evidencias → analizar el malware → eliminar la amenaza
>   → comprobar otros equipos → restaurar → monitorizar
> ```

### 1.1. Quién puede hacer qué

Un procedimiento también deja claro qué se puede hacer directamente y qué necesita autorización. No todo el mundo puede tocar el firewall o cerrar una cuenta.

| Acción | Responsable habitual |
|---|---|
| Clasificación inicial | Equipo de seguridad |
| Aislar un equipo | Equipo técnico |
| Bloquear una cuenta | Administrador autorizado |
| Modificar el firewall | Administrador de red |
| Análisis forense | Personal especializado |
| Comunicación externa | Responsable designado |
| Cierre del incidente | Responsable de seguridad |

> Las guías deben estar **actualizadas** (de nada sirve un contacto o una herramienta que ya no existen) y conviene **probarlas con simulacros** antes de que haga falta de verdad.

## 2. Ciberresiliencia

La **ciberresiliencia** es la capacidad de la organización para aguantar y recuperarse de los incidentes, no solo para evitarlos. Se apoya en cuatro capacidades que forman un ciclo:

```text
ANTICIPACIÓN → RESISTENCIA → RECUPERACIÓN → EVOLUCIÓN
      ↑                                        |
      +----------------------------------------+
```

| Capacidad | Cuándo actúa | En qué consiste |
|---|---|---|
| **Anticipación** | Antes | Prepararse: análisis de riesgos, parches, formación, copias de seguridad, planes de contingencia |
| **Resistencia** | Durante | Seguir funcionando pese al incidente: redundancia, alta disponibilidad, segmentación, respaldos |
| **Recuperación** | Después | Volver a la normalidad de forma controlada: restaurar copias, reconfigurar, verificar integridad |
| **Evolución** | Al final | Usar lo aprendido para mejorar y cerrar el ciclo |

> **La clave de la evolución:** la respuesta no termina cuando el servicio vuelve a funcionar. Si no se aprende nada del incidente, se repetirá. Lo aprendido alimenta una **nueva anticipación**.

> **Ejemplo de resistencia:** si el servidor web principal cae por un ataque, un sistema redundante con balanceo de carga mantiene la web en pie mientras se resuelve. El incidente ocurre, pero el servicio no se para.

## 3. Flujos de decisión y escalado

Durante un incidente hay que tener decidido **de antemano** quién decide y cuándo se escala. Improvisar la cadena de mando en mitad de la crisis sale caro.

El **escalado** puede ser:

- **Interno:** hacia responsables de más nivel dentro de la organización.
- **Externo:** hacia proveedores, equipos especializados u organismos competentes.

Se escala según criterios **objetivos**: severidad, impacto, criticidad de los sistemas, usuarios afectados, información comprometida, duración, riesgo de propagación u obligaciones legales.

```text
Incidente → clasificación → valoración del impacto
      │
   ¿Nivel bajo?
   ┌────┴────┐
  Sí         No
   │          │
Gestión    Escalar → Responsable de seguridad → Dirección
local                      │
                    ¿Necesita apoyo externo? → Proveedor / organismo
```

| Situación | Actuación |
|---|---|
| Incidente de bajo impacto | Lo gestiona el equipo técnico |
| Varios equipos afectados | Escalado al responsable de seguridad |
| Servicio crítico afectado | Escalado a responsables superiores |
| Posible fuga de datos | Escalado a las áreas correspondientes (p. ej. privacidad) |
| Incidente de gran impacto | Se activa el procedimiento de crisis |

> **Cada uno recibe solo lo que necesita.** El flujo no significa que todos sepan todo: a cada destinatario se le da la información justa para su función. Y toda decisión se registra (hora, qué se decidió, quién y por qué), para poder reconstruir después cómo se gestionó.

## 4. Restablecer los servicios afectados

Recuperar un servicio es devolverlo a un estado **operativo y seguro**, y se hace **después** de tener el incidente controlado, nunca antes (si restauras con la amenaza aún dentro, la vuelves a meter).

```text
Servicio afectado → identificar causa → contener → eliminar amenaza
   → restaurar → comprobar integridad → pruebas → restablecer → monitorizar
```

### 4.1. Copias de seguridad

Son la pieza clave para recuperarse de ransomware, borrados o corrupción de datos. Pero antes de restaurar una copia hay que comprobar que:

- Es una copia **válida** y del sistema correcto.
- **No está contaminada** (que no incluya el propio malware).
- Se puede restaurar de verdad y recupera lo necesario.

> Una copia que nunca se ha probado no es una copia de seguridad: es una suposición.

### 4.2. Cuidado con las dependencias

Restaurar solo una pieza no basta si las demás siguen afectadas.

```text
Aplicación web depende de:
   ├── Servidor web
   ├── Base de datos
   ├── DNS
   ├── Autenticación
   └── Red
```

> Si levantas el servidor web pero la base de datos o el sistema de autenticación siguen caídos o comprometidos, el servicio no funciona de verdad.

Antes de dar un servicio por recuperado, se prueban disponibilidad, integridad, funcionamiento, conectividad, autenticación, acceso a datos y controles de seguridad. Y después se mantiene una **monitorización reforzada** un tiempo, por si el incidente reaparece.

## 5. Documentación

Documentar es registrar de forma ordenada todo lo que pasó y lo que se hizo. Empieza en la detección y no para hasta el cierre.

```text
Detección → registro inicial → investigación → decisiones
   → contención → recuperación → cierre → revisión
```

Un registro de incidente suele recoger: identificador, fecha y hora, tipo, severidad, sistemas afectados, descripción, evidencias, acciones, responsable, comunicaciones, estado y condiciones de cierre.

La parte más útil es la **línea temporal de actuaciones**, porque deja la trazabilidad de las decisiones:

```text
10:15  Se detecta actividad sospechosa
10:25  Se clasifica como incidente de nivel alto
10:30  Se aísla el equipo afectado
10:45  Se recopilan evidencias
11:30  Se identifica el origen
12:15  Se eliminan los elementos maliciosos
13:00  Se inicia la recuperación
14:00  El servicio vuelve a funcionar
15:00  Se mantiene monitorización reforzada
```

> La documentación puede contener información sensible (credenciales, datos personales, evidencias), así que se guarda de forma segura y con control de acceso. Sirve además para auditorías y análisis posteriores.

## 6. Seguimiento para que no se repita

Cerrar el incidente **no es el final**. Después toca revisar qué se puede mejorar: la causa, qué controles fallaron, si la respuesta fue eficaz y cuánto se tardó en cada fase.

```text
Incidente → respuesta → recuperación → REVISIÓN
   → identificar mejoras → aplicar medidas → verificar
```

Del análisis salen mejoras concretas:

| Problema detectado | Mejora |
|---|---|
| Sistema sin actualizar | Mejorar la gestión de parches |
| Contraseña comprometida | Reforzar la autenticación (MFA) |
| No se detectó a tiempo | Crear nuevas reglas de monitorización |
| Red demasiado accesible | Mejorar la segmentación |
| Copias insuficientes | Revisar la estrategia de respaldo |
| Usuarios desprevenidos | Reforzar la formación |
| Escalado lento | Revisar el flujo de comunicación |

También se miden **tiempos de respuesta**, que son los indicadores que de verdad dicen si mejoras:

- Tiempo entre que ocurre el incidente y se detecta.
- Tiempo entre la detección y la contención.
- Tiempo necesario para recuperar el servicio.

> **No basta con decir "hay que corregir la vulnerabilidad".** Hay que verificar que se aplicó el parche, comprobar el sistema, validar que la vulnerabilidad ya no está, documentarlo y **revisar otros equipos** con el mismo fallo.

Así la gestión de incidentes se convierte en un ciclo continuo, no en una reacción puntual:

```text
PREVENCIÓN → DETECCIÓN → RESPUESTA → CONTENCIÓN
   → RECUPERACIÓN → REVISIÓN → MEJORA → (de nuevo) PREVENCIÓN
```

---

## Resumen en una frase

Implementar medidas es tener **procedimientos y playbooks** listos para cada tipo de incidente, construir **ciberresiliencia** (anticipar, resistir, recuperar, evolucionar), dejar claro **quién decide y cuándo se escala**, **restaurar los servicios** comprobando copias y dependencias, **documentarlo** todo con trazabilidad, y hacer **seguimiento** para convertir cada incidente en una mejora real.
